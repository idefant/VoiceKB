# Хранилище истории и её связь с повторной отправкой

Область: как хранится история распознаваний, почему выбраны такие механизмы и где слабые места. Пользовательское поведение описано в [ФС «История распознаваний»](../functional-spec/history.md).

## Почему так

**Одна база на приложение, метаданные в SQLite, файлы для аудио.** У приложения одна база данных с несколькими таблицами (`USAGE` — статистика, `HISTORY` — история), а не отдельный файл под каждую область. Владеет ими один `VoiceKBDatabaseHelper`: держать два `SQLiteOpenHelper` на одном файле нельзя (каждый считает, что владеет схемой и версией). Файл называется `voicekb.db`; раньше он назывался `usage.db` (когда хранил только статистику), поэтому при первом обращении к новому имени старый файл переименовывается на месте — накопленная статистика не теряется. Таблица `HISTORY` добавляется аддитивно поднятием версии базы (`onUpgrade`). Метаданные записи (текст, время, длительность, провайдер, модель, имя аудиофайла) лежат в `HISTORY`. Аудио в базу не кладётся: бинарные блобы раздували бы её и усложняли выборку списка — аудиофайлы лежат в каталоге `history/` внутри `getFilesDir()`.

**Кэш — для незавершённой записи, `files/history/` — для сохранённой; перенос вместо копии.** Идущая запись пишется во временный `getCacheDir()`: система сама вычистит брошенное (отмена, сброс, падение до сохранения), и незавершённое изолировано от постоянного хранилища. При завершении распознавания (успех или ошибка) файл **переносится** (`rename`, не побайтовая копия) из кэша в `files/history/`, и в БД пишется строка со ссылкой на имя. Файловый пикер тоже кладёт выбранный файл в кэш, а перенос делает клавиатура при распознавании. Копий не остаётся: повторная отправка перераспознаёт файл, уже лежащий в `files/history/`, и лишь заводит новую строку с тем же именем — несколько записей могут делить один аудиофайл.

**Уборка файлов — сборка сирот, а не привязка «одна запись = один файл».** Поскольку файлы разделяются, удалять файл при удалении строки нельзя вслепую. Удаление одной записи сносит её файл только если на него не ссылается ни одна другая строка. Прунинг по 90-дневному сроку и общий проход собирают «сирот» — файлы в `files/history/`, на которые не ссылается ни одна строка (`SELECT DISTINCT AUDIO_FILE`). Это подсчёт ссылок «без счётчика». Специальной защиты от удаления «свежих» файлов не нужно: незавершённая запись сидит в кэше, а не в `files/history/`, поэтому неучтённых файлов там не бывает.

**Ошибки распознавания — тоже записи истории.** Неудачное распознавание сохраняется как запись с описанием ошибки вместо текста: короткое `message` (показывается) и отдельно `errorDetails` (сырое тело ответа провайдера, под «Подробнее»). Классификация вынесена в `AppError` (`message`/`api`/`transparent`): сетевые/таймаут-ошибки — `transparent` (только сообщение), ответы провайдера — `api` (короткое сообщение + сырое тело). Аудио у ошибки сохраняется, поэтому «Повторить» осмысленно ретраит именно упавшее аудио. Отменённые пользователем распознавания в историю не пишутся.

**Список строится на `RecyclerView`.** История может быть длинной. Наивная отрисовка всех элементов во `ScrollView` держала бы в памяти все View сразу и давала бы лаги прокрутки. `RecyclerView` переиспользует View — это штатное для Android решение и уже применяемый в проекте паттерн. Группировка по дням сделана плоским списком из двух типов элементов (заголовок дня и запись), а не вложенными контейнерами.

**Воспроизведение — системный `MediaPlayer`.** Проигрывается один короткий локальный клип по нажатию; для этого достаточно `MediaPlayer`, отдельная медиа-библиотека не нужна. Плеер один на весь список: старт другой записи останавливает предыдущую. Полоса прогресса обновляется тиком раз в 250 мс, перемотка идёт через `seekTo`.

**Повторная обработка переиспользует запрос клавиатуры.** Логика распознавания вынесена в `HistoryReprocessor` и повторяет запрос, который шлёт клавиатура (провайдер, модель, язык, стилевой промпт, прокси, ретраи). Клавиатура при этом сохраняет свою встроенную версию запроса — её ретраи и поведение сессии задокументированы отдельно и не переносились ради снижения риска.

## Связь с повторной отправкой

Кнопка повторной отправки на клавиатуре берёт аудио последней записи истории, а не отдельно сохранённый «последний файл». Раньше существовал отдельный указатель в настройках (`resend_file_name` / `last_file_name`); он удалён, источником истины стала история.

Следствия:

- Отменённые и сброшенные записи не попадают в историю, поэтому не могут стать целью повторной отправки — инвариант «удалённый фрагмент не становится целью повтора» сохраняется естественно.
- Удаление самой свежей записи истории меняет цель повторной отправки на следующую по свежести (или снимает её, если история опустела). Клавиатура пересчитывает цель при показе и после каждого распознавания.

## Слабые места

- **Гонка процессов.** Клавиатура (IME) и экран истории живут в разных процессах одного приложения, но пишут в одну базу. Пересчёт цели повторной отправки на клавиатуре происходит при показе и после распознавания, а не мгновенно при удалении записи на экране истории — короткое расхождение возможно, но безопасно (цель проверяется на существование файла перед отправкой).
- **`prepare()` на главном потоке.** Плеер готовит локальный короткий файл синхронно; для таких файлов задержка мала, но на очень длинных записях возможна кратковременная заминка.
- **Окно между переносом и записью строки.** Файл переносится в `files/history/` и лишь затем регистрируется строкой БД — между этими шагами он формально не учтён. Оба шага идут подряд в фоне одного распознавания, окно микроскопическое; чтобы его задеть, сборка сирот с экрана истории должна выполниться ровно в этот момент, что на практике не происходит.
