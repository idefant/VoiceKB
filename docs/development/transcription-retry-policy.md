# Политика повтора запросов транскрипции

Главный файл: `app/src/main/java/com/idefant/voicekb/VoiceKBUtils.java` (метод `isTransientTranscriptionError`).

Связанный раздел ФС: [Голосовая сессия и возврат к клавиатуре](../functional-spec/voice-session.md) (состояние «Отправка»).

Область описывает, при каких ошибках запрос к провайдеру распознавания повторяется автоматически. Политика едина для двух вызовов: живой транскрипции в `VoiceKBInputMethodService` (состояние «Отправка») и повторной обработки записи из истории в `HistoryReprocessor`. Классификация самих ошибок для показа пользователю (`AppError`) и хранение ошибок как записей истории вынесены в [Хранилище истории](history-storage.md).

## Повтор классифицируется по HTTP-статусу, а не по тексту ошибки

Раньше «повторять или нет» решалось поиском подстрок в тексте ошибки (`api key`, `quota`, `audio duration`, …): всё, что не совпало со списком, считалось временным сбоем и повторялось. Это чёрный список наоборот — любая неучтённая ошибка попадала под повтор. В частности, неверный заголовок в дополнительных параметрах отдаёт 400, текст которого не совпадал ни с одной подстрокой, поэтому запрос повторялся 3 раза с фиксированными паузами `Thread.sleep(3000)` — пользователь ждал ~9 секунд перед постоянной по своей природе ошибкой. Неверный API-ключ при этом падал мгновенно только потому, что его текст случайно содержал `api key`.

Теперь решение опирается на типы исключений `openai-java`, а не на текст:

- повторяем сетевые ошибки/таймауты (`OpenAIIoException`), явно повторяемые (`OpenAIRetryableException`), ошибки сервера (`OpenAIServiceException` со статусом ≥ 500) и лимит запросов (429);
- НЕ повторяем клиентские ошибки 4xx (400/401/403/404/422 — неверный заголовок, ключ, формат, размер): они постоянны, повтор бесполезен;
- исчерпанную квоту (429 с `quota` в тексте) тоже НЕ повторяем — за несколько секунд она не восстановится. Это единственное место, где статус 429 дополнительно уточняется по тексту.

**Что подразумевает:** ошибка конфигурации теперь показывается сразу, без задержки в ~9 секунд. Downstream-логика выбора пользовательского сообщения (`e.getMessage()` → «invalid_api_key», «quota_exceeded» и т.д.) не затронута — она получает то же исключение, просто без лишних повторов. Неизвестные (не-`OpenAI*`) `RuntimeException` считаются постоянными и не повторяются (fail-fast).

**Что подразумевает по отмене:** цикл повтора прерывается сразу при отмене пользователем — `speechApiThread.shutdownNow()` / `reprocessExecutor.shutdownNow()` прерывают поток, поэтому проверяются `Thread.currentThread().isInterrupted()` и причина `InterruptedIOException`. Прерывание во время паузы `Thread.sleep` восстанавливает флаг прерывания и выходит из цикла, а не проглатывается молча.

**Слабое место / компромисс:** уточнение квоты по подстроке `quota` остаётся текстовой эвристикой и языкозависимо — если провайдер вернёт текст квоты иначе, запрос повторится 3 раза перед отказом (деградация в старое поведение, не поломка). Пауза между повторами фиксированная (3 с), без экспоненциального роста; для 429 это может быть мало, но менять тайминг в рамках этой правки не стали. Клиент `openai-java` может иметь собственные встроенные повторы поверх этого цикла — здесь это не настраивается.
